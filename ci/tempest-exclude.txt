# ShareMultiBackendTest
#   The test builds a backend->protocol map by calling list_pools() and keying
#   on share_backend_name.  With our two-backend topology (weka_nfs /
#   weka_wekafs) the weka_nfs backend's pool may be absent from the pool list
#   when weka_nfs_server discovery fails at redeploy time (the NFS backend
#   cannot report its pool until the gateway IP is resolved and the backend
#   restarts).  This produces a KeyError: 'weka_nfs' inside resource_setup,
#   failing every test in the class before any share is created.
#
#   The multi-backend property itself (two share_backend_name values, separate
#   hosts) is already validated by the per-backend lifecycle and quota tests.
#   ShareMultiBackendTest adds no coverage we lack; it is skipped here rather
#   than worked around with a guard in tempest.conf because the skip is the
#   correct response to a test that assumes all configured backends are
#   pool-reporting.
manila_tempest_tests.tests.api.admin.test_multi_backend.ShareMultiBackendTest
#
# AccessRulesMetadataTest
#   resource_setup() hardcodes IPv6 addresses for `ip`-type rules
#   (access_to['ip'] = {rand_ipv6_ip() ...}). The Weka driver is IPv4-only
#   for ip access rules (Weka NFS client-groups and WEKAFS security policies
#   are configured with IPv4 CIDRs), so the seeded IPv6 rule goes to `error`
#   and the class setup fails. The access-rule *metadata* API semantics this
#   class covers are protocol/rule-type agnostic and exercised elsewhere;
#   skipping is the correct response to a test that assumes IPv6 support.
manila_tempest_tests.tests.api.test_access_rules_metadata.AccessRulesMetadataTest
